## 0b. Eleven strategic reports a day, each, about a marketplace with no activity — FIXED

`exec_reports` holds **44–45 rows per officer over 10–13 Aug** — about **eleven per officer per
day**, six officers. Over those same four days the marketplace took 0 inquiries, 0 quotes and 0
trades, so the metrics were very often byte-identical between runs. One of the reports says so in
its own words:

> "All provided metric arrays (price_spread, monthly_volume, category_growth,
> competitive_categories) are empty, so no trend, competitiveness, volatility, or seasonality
> analysis can be performed at this time."

**Only one is ever read.** Every consumer reads the *newest* report per officer — `exec_agents`'s
own header says so. Ten of every eleven were synthesised on sonnet-5, billed, filed and never
looked at. `exec_reports.period` is a DATE: one report per officer per period is what the schema
has always implied, and nothing enforced it.

**Fixed by guarding on the INPUT, not the clock.** If a report already exists for this officer and
period *and* the metrics rpc returns exactly what that report was built from, no model is called.
The moment one number moves, a fresh report is produced on the same tick with no delay — this
throttles silence, not work, and trading will make the metrics move constantly.

Verified by execution on production: run 1 filed report 315 and made **1** model call; runs 2 and 3
returned `unchanged: true, ai: false, attempts: 0` and made **0**. The unchanged path returns a
true sentence rather than `null`, because `fn_action_invoke_collect` fills
`org_tasks.result.deliverable` from that field and ten routines read it.

**Estimated saving at the current run rate: `exec_agents` from ~95 model calls a day to ~6 —
of the order of AED 120/month.** That is the largest single saving in this audit and it costs no
quality at all: a duplicate report of unchanged metrics carries zero information.

## 2. Why `agent_brain` sends 13,000 tokens a call

The 13,151 figure in the brief is the average across *two different* calls `agent_brain` makes per
turn. Split apart:

| Path | Model | Calls | avg input | 30d AED |
|---|---|---:|---:|---:|
| `agent_reasoning` — the actual turn | `anthropic/claude-sonnet-5` | 408 | **21,694** | 91.55 |
| `memory_retrieval` — the auto-learn pass | `google/gemini-3.1-flash-lite` | 365 | 2,512 | 0.90 |
| (July, unclassified) | sonnet / opus | 46 | ~21,000 | 15.17 |

**So the real number is 21,694 tokens, not 13,151, and 93% of `agent_brain`'s tokens are input.**

### What is actually in it — measured

The turn is not one runaway dump. It is **six separately-bounded blocks, and nothing owns the
total.** For `procurement`:

| Block | Chars | Bounded by |
|---|---:|---|
| Employment context (`fn_agent_context_capped`) | ~24,000 | `p_max_chars` passed by `agent_brain` |
| `LIVE DATA SNAPSHOT` — `JSON.stringify(ctx).slice(0,9000)` | up to 9,000 | a blunt `.slice()` in `agent_brain` |
| Conversation history — 6 turns × 1,200 | up to 7,200 | `HIST_TURNS` / `HIST_CHARS` |
| Base system prompt (doctrine, teamwork, `@@ACTIONS@@` contract) | ~4,000 | hard-coded |
| `kb_search` retrieval — 10 chunks × 400 | up to 4,000 | `retrieve()` |
| Handoff inbox + standing founder instructions | variable | — |
| **Total** | **≈ 48,000 chars ≈ 21,700 tokens** | **nobody** |

Each block is individually defensible. Their sum is what costs AED 91.55 a month, and no single
place in the code looks at it.

**I was wrong in my first pass and the correction matters.** I initially reported that LAYER 1 was
serving irrelevant domain shards — asked about *"marble worktops for a villa kitchen"* the context
contained `## 1. Public Health, Medical Gas, and Specialist Building Services` and
`## Structural Engineering: UAE Knowledge Library Shard`. Those are **LAYER 2b/2c**, which are
retrieved *for the question* by `fn_dept_library_search` and `fn_ops_knowledge_search`. They are
correctly query-scoped and should stay. The retrieval side of this prompt is working.

### What LAYER 1 really is, and the defect inside it

LAYER 1 is built from `agent_knowledge` rows with `agent_key = '_global'`, appended whole:

```sql
piece := '## '||r.topic||E'\n'||r.content||E'\n\n';
if length(out)+length(piece) <= cap then out := out||piece; end if;
```

There is **no per-item cap** — only a whole-context cap, applied per item. Two consequences,
measured:

1. `## company:self_knowledge` is a **4,027-character single row** that lands in every employee's
   prompt on every turn — ~1,800 tokens, ~AED 5.4/month on `agent_brain` alone.
2. Worse, and not a cost problem at all: **`## Company FAQ (canonical answers)` is 197,956
   characters at priority 96** — the highest-priority global knowledge row in the company. It can
   never satisfy `length(out)+length(piece) <= cap`, so it is **silently skipped on every call, for
   every employee, and lower-priority rows are delivered in its place.** The guard does not truncate
   the item, it drops it. Nothing logs that. There are also several `## Asset text: …` rows at
   exactly 8,000 characters (`DATABASE_SCHEMA.md`, `EDGE_FUNCTIONS.md`, `01_EXECUTIVE_SUMMARY.md`)
   sitting in the same table at priority 45.

### The shrink that was done — the `LIVE DATA SNAPSHOT`

`context()` was fetching the last 15 `agent_actions` rows **including their full `detail` jsonb**
and 12 `agent_runs` rows **including `counts`**, then cutting the lot with `.slice(0, 9000)`.

`detail` is the executor's working record. For an item `action_worker` has settled it holds the
**entire deliverable — up to 20,000 characters — under `detail.deliverable`.** So the employee was
being handed back the full text of work it had already done, fifteen items deep, inside a
9,000-character budget. `counts` is the same shape for runs: `prompt_chars`, `stable_chars`,
`history_turns` — instrumentation about a *previous* call, not context for this one.

Worse than the tokens: the blunt `.slice(0, 9000)` cuts from the **end**, and the `company` block —
the live figures the system prompt calls *"the ONLY valid source for operational numbers"* — was
**last in the object**, so it was the first thing any truncation deleted.

Fixed in `agent_brain` today: the two jsonb blobs are no longer selected, `recommendation` is capped
at 240 characters, and `company` now comes **first** so a truncation can never remove it again.

**Measured on production, same two-turn probe before and after:**

| | turn 1 prompt tokens | turn 2 prompt tokens |
|---|---:|---:|
| before | 17,793 | 16,869 |
| after | **16,677** | **15,628** |

**≈1,200 tokens per call, ~7% of `agent_brain`'s input — about AED 3.6/month.** Less than the
~AED 10 I estimated before measuring, because the snapshot was not filling its full 9,000-character
budget. The cache still hit on the same probe (8,578 written, then read), confirming the snapshot
lives in the volatile half and the stable prefix is untouched.

**Still recommended, not built:** a per-item cap in LAYER 1's two loops (`left(r.content, 1500)`),
which would bound the worst case forever and let the 197,956-character FAQ deliver its first 1,500
characters instead of nothing. That is inside `fn_agent_context` — the routine with a documented
history of one inserted line silently evicting knowledge from 19 employees — so it is measured and
written up rather than rushed in at the end of a long session.

## 3. Prompt caching — built, measured, switched on

### It was off for a good reason, and the reason was not the one recorded

The plumbing all existed: `agent_brain` splits its prompt, passes `sys_stable`, and `ai_gateway`
stamps `cache_control` on that block. The note in `ai_gateway` said to re-measure and move the
switch.

**The block was not byte-stable.** Hashing the first 19,500 characters returned for `procurement`:

| Time (UTC) | md5 of the "stable" prefix |
|---|---|
| 03:10 | `a7f351e2402d7924c753b8311f19f338` |
| 03:18 | `03d70254f5c241f86a4def35cb4a8d39` |
| 03:30 | `d2eaa6c942ba0f34fce9e2fb937faa54` |
| 03:55 | `b26a841a215976cb3035b08f7aac6188` |

Four prefixes in 45 minutes. At 03:55 all three *different questions* returned the same hash, so it
is not the question — it is time. The head contains `# YOUR CURRENT WORKLOAD (live)`, `# WHAT THE
COMPANY IS WORRIED ABOUT — its own live risk register` and `## Pricing & fees (LIVE — auto-synced)`;
`org_tasks` moved from 999 to 1,014 rows during that same window.

`fn_agent_context_capped` claimed *"head is left() to a CONSTANT length, so for a given agent and
budget these bytes are identical on every call."* Constant **length** is not constant **bytes**.
Turning the switch on against that block would have bought a 1.25× cache write on every call and
read none of it — it would have **raised** the bill. The 0.1% hit rate already in `ai_cost_log` is
that fact in the ledger.

### What was built

`agent_context_head` stores the prefix per employee; `fn_agent_context_head_refresh()` rebuilds it
every 6 hours (cron `agent_context_head_refresh`, `40 */6 * * *`, both projects);
`fn_agent_context_capped` serves the stored bytes and **falls back to live assembly** if the row is
missing, stale beyond 3 hours, or built for a different budget. 17 employees cached on production,
5 on staging, 0 failures. It also takes a 700 ms+ context assembly off every agent turn.

### Measured before and after, on production, by execution

Two real `agent_brain` turns for `procurement`, 8 seconds apart:

| | prompt tokens | cached in | cache write | output | AED |
|---|---:|---:|---:|---:|---:|
| turn 1 (03:31:10) | 17,793 | 0 | **8,578** | 593 | **0.1682** |
| turn 2 (03:31:18) | 16,869 | **8,578** | 0 | 115 | **0.0714** |

Turn 2 read 8,578 cached tokens — **51% of its input**. Solving the two calls for the input and
output rates gives ≈ AED 7.34 per million input tokens; the same turn without the cache would have
cost **AED 0.1281 against the 0.0714 it did cost — 44% off that turn.**

### The honest expectation, which is smaller than 44%

A hit needs the same employee to call back inside the TTL. Measured over 7 days, 267
`agent_brain`/`agent_reasoning` calls with a prior call across 14 employees: **34.5% within 5
minutes**, 72.7% within an hour, median gap 59.6 minutes.

At the provider default TTL (5 min, 1.25× write, 0.1× read, break-even 21.7%):

> block cost × (0.345 × 0.1 + 0.655 × 1.25) = **0.853** → **14.7% off the cacheable block**

The block is 8,578 tokens × 408 calls × AED 7.34/Mtok ≈ **AED 25.7/month**, so the saving is of the
order of **AED 3.8/month**, growing as the other `agent_reasoning` callers adopt `sys_stable`
(none of `action_worker`, `exec_agents` or `workflow_dispatch` pass it today).

**The brief called prompt caching "the single biggest saving available". Measured, it is not — it
is worth single-digit dirhams a month.** The 1-hour TTL would roughly double that (72.7% against a
52.6% break-even, ≈ AED 9.8/month) and is deliberately left as its own separately-measured change:
its downside is a 2× write premium instead of 1.25×, and a 59.6-minute median sits exactly on its
boundary.

**The biggest saving available is §0: the large tier is 76.4% of the bill.**

`org_tasks` holds **999 rows**: 385 assigned, ~55 proposed, the rest closed.

### By what raised them

**381 of the 385 assigned tasks have `action_class = 'analysis'`**, and they are almost entirely

|---|---:|---:|---:|---:|

| `test.failed` | 36 | 27 | 1.3 | 2 |
| `security.event` | 36 | 18 | 2.0 | 2 |
| `priority.updated` | 20 | 20 | 1.0 | 1 |
| `quote.received` / `outcome.graded` / `os.health_changed` / … | ~150 | mostly 1.0 | | |

**282 of the 999 rows are exact `(department, title)` duplicates; 71 of those are still open.**
`test.failed on scheduled_run route_inquiry` exists eight times for `knowledge`. Fifteen distinct
`Supply gap: …` titles exist five times each. One completed task records the position in its own
words: *"Closed the 27-July verified_suppliers event as the ninth duplicate."*

**416 tasks were minted on 6 August alone**, against a 3–9/day baseline.

### What they produced

Completed `analysis` tasks carry a `result` averaging ~3,900 characters — a written deliverable,
reviewed by another agent and marked `published`. That is a genuine work product. The question is
whether it was worth buying, and for the recurring ones it demonstrably was not: **`knowledge` was
answering `test.failed on scheduled_run uptime` once an hour** — tasks 721, 722, 723 closed at
00:50, 01:50 and 02:50 on 14 Aug — because the test keeps failing, so the condition stays true.

### Is it busywork the AI invented for itself? Partly, yes — and here is the mechanism

`fn_event_dispatch` already deduplicates, but **only against an OPEN task**:

```sql
where t.decided_by = 'fn_event_dispatch' and t.dept_key = v_dept and t.title = v_title
  and t.status not in ('done','closed','cancelled')
```

That is right for a burst and wrong for **a condition that stays true**. `verified_suppliers` is
missed because we have one confirmed supplier. `reveals_30d` is missed because we have not traded.
Neither stops being true because an employee wrote 4,000 characters and closed the row — so the
next tick finds nothing open, mints a fresh task, and buys another large-tier deliverable
answering the question that was answered an hour ago.

**Fixed today** (`a_question_that_was_answered_three_hours_ago.sql` +
`the_cooldown_i_just_shipped_could_never_fire.sql`): a recurrence cool-down, default 7 days, set by
`decision_policy.event_recur_cooldown_days`. If a department already closed an identically-titled
bus task inside the window, the event attaches to *that* task instead of raising a new one. Nothing
is closed, deleted or back-dated; the `event_delivery` row still links the event to the answer, and
a new `suppressed_recurring` counter makes the saving visible.

Proven by an aborted-transaction probe on production: emitting `test.failed / scheduled_run /
archive_rfq` attached the `knowledge` delivery to **closed task 721** instead of minting, while
`qa` — which has no closed copy inside the window — correctly still minted one.

**Measured counterfactual: 9 of the 133 bus tasks minted in the last 7 days would have been
suppressed (6.8%).** At roughly AED 0.05–0.22 a task that is single-digit dirhams a month. It is
worth having because it stops an unbounded treadmill, not because it is a large sum.

### What I am proposing, not doing

**The 71 open duplicate tasks and the 244 still-assigned tasks minted on 6 August should be
closed.** I have not closed them. Mass-closing work rows is close enough to a destructive
production change that it is the founder's call, and the standing rule against mass-closing to
make a number look better applies. The cool-down stops new ones; clearing the backlog is one
`update` away on your word.

**They were not decoration in the "nobody reads them" sense** — `fn_ai_route`, `fn_ai_spend_guard`

**They were decoration in a worse sense: the guard could not fire.**

### New numbers, set today

```

                                           0.10 × the previous budget,  -- keeps your ranking

```

Three terms because any one alone is wrong: 3× measured would set procurement to AED 4 and strangle
the department you have deliberately funded highest the moment we start trading; your ranking alone
is what we have now, with exec funded below departments that have never made a model call; and the
AED 40 floor means a department is not halted on its first real task.
