# Load test, 11 Nov 2026: can 100 people chat at once without the company falling over?

Seat: **it_engineer**. Founder ruling 1622 (10 Nov 2026): *"scalable — e.g. 100 customers chatting at the same time
must not crash the company."* Ruling 1606: no paid upgrades now. Runs: 11 Nov 2026, 00:00 to 00:40 UTC (04:00 to 04:40
Dubai), against production `htdblwldjkcgjvmqkbeh` and `quotesdone.com`.

**The short answer.** Not yet proven, because the chat test itself could not run. Its model stub has to be deployed
first, and this session was told not to deploy. Every other part of the chat path was measured. Nothing failed outright
up to 200 visitors browsing the site, up to 400 users hitting the public functions, and 50 inquiry writes at the same
moment. **The first thing to give way is `embed_ml`**, the free in-house text embedder that every chat turn calls
several times. A burst from cold failed 7 to 15% of its requests for about 10 seconds while new workers started. Warm,
it holds about 29 embeddings a second, and fails 3% at 46 a second. When it fails, a chat turn gets a weaker answer, not
an error page (the code's null path is pinned by tests; it has not yet been seen under load). The fix for the burst
failures is on this branch. Section 6 shows how to run the real 100-chat test.

How to read the labels: **[M]** measured today, **[D]** documented by the vendor (doc read today unless it says
otherwise), **[C]** read from our code or config today, **[A]** assumed (a planning figure, stated as one).

## 4. Inquiry writes at the same moment, nothing committed (`db_write_burst.mjs`)

Each probe inserts a ZZ DEMO customer at `qd-zzload…@example.invalid` and a `sent` inquiry for it, so every trigger on
both tables fires. It then runs `fn_match_capability` and raises. The times are taken inside the database.

| concurrent | probes | total p50 / p95 / max (ms) | customer insert p50 | inquiry insert p50 | match p50 |
|---:|---:|---|---:|---:|---:|
| 1 | 3 | 90 / 93 / 93 | 19 | 36 | 35 |
| 10 | 30 | 203 / 354 / 357 | 28 | 83 | 73 |
| 25 | 75 | 808 / 923 / 951 | 105 | 351 | 313 |
| 50 | 118 of 150 | 1,449 / 2,258 / 2,385 | 203 | 648 | 604 |

At 50, 32 probes were refused by the **management API's** throttle (HTTP 429). That is a limit of the test harness, not
of production. The time grows almost exactly in step with concurrency, about 29 ms for each extra probe, and no lock
waits were seen. That is CPU queueing on the two shared cores, not contention between rows. At that rate the ceiling is
about 22 to 35 intakes a second. The capacity plan's launch peak is 2 a minute [A], and its tenfold target is 20 a
minute. One probe's trigger profile (`track_functions` set for its transaction only): `fn_event_dispatch` 13.4 ms over
3 calls, `fn_emit_customer_registered` 11.8 ms, `scrub_inquiry_contacts` 11.1 ms, `fn_backup_kick` 6.5 ms,
`fn_rfq_score` 5.2 ms. No single routine stands out, so there is no index or query to fix here. The test's matcher
returned 0 suppliers for plumbing in Dubai, so a real match with suppliers costs more than these figures.

## 5. Fixes made on this branch

| fix | file | why (measured) | prevented by | before → after |
|---|---|---|---|---|
| **A worker killed under load is asked once more.** `embed_ml` `gte`/`query` read a model and write nothing, so a 546 is retried once after 400 ms, the same as a relay 503 already was. | `supabase/functions/_shared/ml_embed_client.ts` | 5 of 69 and 8 of 104 embeddings were 546 in the cold bursts | `_shared/embed_failure_reason.test.ts` (a 546 then a vector = 2 calls and a vector; two 546s = 2 calls and null; 13 passed, and it fails when the retry is removed) | before: each 546 is a null vector (a weaker answer). After: **not measured, not deployed.** It needs the 22 functions that bundle the module (section 6). Watch-out: under sustained overload a retry adds up to the failure rate in extra load (3 to 15% here). |
| **A load-test mode for the chat path that cannot reach a real person or a model.** | `supabase/functions/_shared/load_stub.ts`, `ai_gateway/handle.ts` | the existing no-spend answer is the outage shape (HTTP 503), so a load test on it would measure a different, shorter turn | `ai_gateway/load_stub.test.ts` (10 tests against the real handler, incl. the control that the same request without the tag DOES reach the provider; 6 fail when the stub is switched off) | n/a |
| **A load run spends its own limiter buckets.** | `site_assistant/index.ts` (`limiterScope`) | 300 load turns would otherwise use 300 of the 1,500 real visitor messages a day | `_shared/load_stub.test.ts` | n/a |

The stub answers only when **all four** of these hold: (1) a **proven** run tag (`e2e_run.ts`: the service-role bearer
or the internal secret; a typed header is dropped); (2) that tag's open window was opened by `load_test`; (3) the window
has `models_allowed = false`; (4) the request names no subject, or names a fixture. A real subject, or a fixture check
that fails, is refused with HTTP 503 `load_stub_refused` and is never sent. A real visitor carries no proven tag, so for
them the code returns "normal" before it reads anything. The stub writes one `fn_llm_log` row (model `load_stub`,
cost 0). It writes no `llm_attempt` row and touches no breaker. It is never written to `llm_cache`.

**What was not fixed here, and why.** There is no query or index to fix on the write path (section 4). The cost is
spread across the triggers. The WhatsApp region (wa_inbound in us-east-1) needs the Twilio webhook URL to carry
`?forceFunctionRegion=ap-southeast-1`. That is a production change to Twilio's settings, and the signature check
already signs the query string. It is not made here (no production change was allowed).

## 6. To run the 100-chat test (needs a deploy)

1. Deploy two functions from this branch: `node scripts/deploy_functions.mjs --ref=htdblwldjkcgjvmqkbeh --production
   ai_gateway site_assistant`. That carries the stub and the 546 retry for those two. At merge, the other 20 that bundle
   `_shared/ml_embed_client.ts` pick up the retry: accountant, ceo_agent, customer_api, email_triage, inbound_email,
   inquiry_intake, it_engineer, marketing, marketing_channels, marketing_outreach, marketing_social_inbox, public_site,
   quote_compare, quote_extract, resend_inbound, resilience_ping, sales_engineer, supplier_api, supplier_portal,
   wa_inbound. No SQL file is involved.
2. At a quiet hour: `QD_FIXTURES=1 NODE_USE_ENV_PROXY=1 QD_LOAD_ANON_KEY=<quotesdone2 publishable key>
   QD_LOAD_RUN_SECRET=<app_secrets.cred_db_internal> QD_LOAD_GATEWAY_SECRET=<app_secrets.cred_fn_ai>
   node scripts/load/chat_load_run.mjs --stages=10,50,100 --stage-seconds=90 --out=<scratch>/chat.json`
3. Two gates must pass before any turn is sent. A **preflight** calls `ai_gateway` as `load_probe` and needs the answer
   `load_stub`; the gateway deployed today answered `fixture_no_spend` (HTTP 503, AED 0). A **spend guard** runs
   between stages and aborts on any paid model or any cost, on every `site_assistant` / `load_probe` / stub row since the
   start. After the run, teardown runs in a `finally` (and on a signal), then counts what is left; it exits 2 if anything
   was left or any notification names the run.

**Found while building the guard.** `ai_cost_log.e2e_run_tag` is NULL on every row of a load run. The tagging trigger
keeps a tag only while `fn_e2e_run_tag_open` says the window is open, and that needs `models_allowed = true`, which a
load window never is. So the guard reads a wider set of rows than the run's own, as described above, and does not use
the tag (TD-26).

## 7. What breaks first, and how far the current plan goes

1. **`embed_ml` on a fast ramp.** At about 10 embeddings a second from cold it fails 7 to 15% for about 10 s. Warm, the
   ceiling is about 30 to 45 a second. 100 people chatting at once is about 5.5 turns a second [A: 8 s model, 8 s
   reading, 2 s our own work], which is 16 to 33 embeddings a second [C: 3 to 6 per turn]. That is inside the warm
   ceiling and above the cold one. **A campaign that brings 100 people in within a minute after a quiet night will see
   the burst.** In the code, every embedding failure is a null path, so the reply goes out without semantic FAQ, recall
   or trade-knowledge matching. The page does not error.
2. **The website's daily chat ceiling (1,500 visitor messages a day in total)** is a deliberate spend cap, not a
   capacity limit. 100 visitors at 15 messages each use it up. After that everyone gets the polite "sign up" reply for
   the rest of the day.
3. **The database on writes.** 22 to 35 intakes a second on the current 2 shared cores. That is about 60 to 100 times
   the assumed launch peak.
4. **Never reached:** website pages (200 users, 98% CDN hits) and public functions (400 users, in-region p95 under 100
   ms). Connections peaked at 31 of 120 direct.

**On the current plan (ruling 1606, no upgrade):** 200 people browsing at once, 400 at once on the public reads, about
20 intakes a second, and a chat load that grows steadily rather than arriving in one burst.
