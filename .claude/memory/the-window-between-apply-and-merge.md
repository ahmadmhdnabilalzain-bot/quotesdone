This repository deploys by the **production-direct protocol**: `scripts/apply_sql.mjs <file> --apply`
posts the committed bytes to production and reads the definitions back, and the PR follows. So
between the apply and the merge, **production is genuinely ahead of `main`** — and the checks that
compare them are supposed to say so.

Hit twice on 18 Aug 2026 in one session:

- `repo and database agree` on `main@301ecb0` at 05:59 — the parity job, because production carried
  six routines and a view that `main` did not yet.
- `repo and database agree` on `main@0666771` at 07:11 — `application_source_of_truth`, because
  `a_row_id_is_not_a_key.sql` had been applied to production minutes earlier and its PR was still
  open.

Both cleared on the next push after the merge. **Neither was a defect and neither should be
"fixed".** A gate that stayed green while production ran code no committed file described would be
the actual defect.

**How to apply:**

- A red `repo and database agree` on `main` during a session that has applied SQL is expected. Check
  the failing job names against what you applied before treating it as a regression: `parity`,
  `application_source_of_truth` and `canonical_routine_manifest` are the three that see this window.
- Close the window by merging, not by reverting the apply.
- A PR branched off `main` BEFORE such a merge inherits the same red — merge `main` into it rather
  than debugging the check. That is what happened to PR #439.
- The artefacts move with the code: `supabase/schema/full_schema.sql` (regenerate with
  `export_from_either_source_is_identical.mjs --write`), `CANONICAL_ROUTINE_MANIFEST.csv`
  (regenerated by running the engine), and any committed CSV the change touches. Three separate
  catch-ups were needed in one branch for exactly this.
