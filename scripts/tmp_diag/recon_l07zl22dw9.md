### Is there ANY path by which a real authenticated founder session could be driven from this repo without the founder personally acting?

**YES — measured, not inferred. I did not execute it.**

The chain, each link measured:

1. `public.fn_phase_c_founder_subject_bind(uuid)` is `SECURITY DEFINER` and its only caller guard is
   `if current_user in ('anon','authenticated') then raise … (pd_founder_bind_untrusted_caller)`.
2. `EXECUTE` on it is granted to **`{postgres, service_role}`** (`aclexplode(proacl)`).
3. This repo's reader executes as **`current_user = postgres`** — measured directly. `postgres` is neither `anon` nor `authenticated`, so the guard passes.
4. `postgres` can `SELECT auth_user_id` from `public.phase_c_founder_identity`; both active email identities have one, and both resolve to a real row in `auth.users` (measured with `exists(select 1 from auth.users u where u.id = f.auth_user_id)`).
5. `fn_phase_c_founder_subject_bind` then inserts the audit row and `perform set_config('app.phase_c_founder_auth_event', v_ev::text, true)`, after which `fn_phase_c_require_founder` Route B returns the founder's identity for the rest of that transaction.

So a script in this repo can mint a founder-authenticated transaction and satisfy `fn_phase_c_refund_decision_guard`. It is **not silent**: `phase_c_founder_auth_event` (currently **0 rows**) would record `route='server_verified_subject'`, `txid`, and `bound_by = current_user = postgres`, and it is write-guarded so the row cannot be suppressed.

- **Does a COMMITTED kernel run created through the canonical services let the injection be attempted without a direct write to a kernel-owned table?**

## PD-CONC-001 — exactly what two sessions must claim

- **There is no task claim.** `public.phase_c_task` has columns `accountable_role_id, manager_role_id, reviewer_role_id, state, blocker, …` — no `claimed_by`, no `claimed_at`, no `locked_until`. Its states in production are only `queued / completed / cancelled`. Its sole mutator with write authority is `fn_phase_c_task_transition(bigint,text,text,jsonb)`, which uses **plain `FOR UPDATE`** (`select * into t from public.phase_c_task where task_id = p_task_id for update;`) — **no `SKIP LOCKED`, no advisory lock**.
- **The routine that behaves as a claim** is `public.fn_kernel_handoff_accept(jsonb)` on **`public.phase_c_handoff_run`**: it takes `phase_c_workflow_run … for update` then `phase_c_handoff_run … for update` (stated lock order), then `if hr.status <> 'open' then raise … (k3_handoff_not_open)` errcode `23514`. Two sessions racing the same `handoff_run_id`: the second blocks on the row lock, then sees `status <> 'open'` and is refused by name. That is a correct one-winner design **without** `SKIP LOCKED` — the refusal is the status check, the lock only serialises it.
- **`FOR UPDATE SKIP LOCKED` exists in exactly three places**, none of them a task: `fn_phase_c_outbox_claim(integer)` on `phase_c_event_outbox` (`order by outbox_id for update skip locked limit greatest(1, coalesce(p_limit,20))`), `fn_kernel_outbox_deliver(integer,text)` on the same table, and legacy `fn_workflow_step_claim(integer)` on `public.workflow_step_run` (`for update of sr skip locked`).
- **No advisory lock anywhere in `public`** (0 routine bodies contain `pg_try_advisory`).
- **What two sessions would need:** one committed `phase_c_handoff_run` with `status='open'` and a resolvable receiving role, plus two real Postgres connections (the Management-API helper serialises statements and cannot produce a race).
