# scripts/sql/SUPERSEDED.txt — DEFINITIONS THAT MAY NEVER WIN, STATED OUT LOUD.
#
# scripts/sql is append-only: a file is a record of a change that was applied, and it is never
# edited afterwards. That leaves one gap. When two files define the same routine and the older one
# is simply wrong now, the apply order in MANIFEST.txt already decides the winner — but nothing in
# the repository SAYS the loser is retired. A reader opening the older file has no way to know, and
# a future session can edit and apply it in good faith.
#
# This file closes that gap without falsifying a historical record. Each line names a (file,
# routine) pair that is superseded, the file that supersedes it, and why.
#
# FORMAT   <superseded file> :: <routine> :: <superseded by file> :: <reason>
#
# scripts/checks/canonical_routine_manifest.mjs reads this file. A definition listed here is never
# eligible to be canonical, whatever the apply order would otherwise say.

scripts/sql/operations_assistance_company_reports.sql :: fn_ws_operations :: scripts/sql/operations_company_remaining_lists.sql :: Both files were added in commit deff052 (PR #417) and both define this routine with different bodies. The final Phase C acceptance (17 Aug 2026) found sql_files_match_live certifying the pair as clean because it accepted live matching EITHER candidate from the newest commit. The deployed body is the one in operations_company_remaining_lists.sql, which is also the later file in MANIFEST.txt. This definition is retired.

scripts/sql/operations_assistance_company_reports.sql :: fn_ws_company :: scripts/sql/operations_company_remaining_lists.sql :: Same commit, same pair of files, same defect as fn_ws_operations above. The deployed body is the one in operations_company_remaining_lists.sql. This definition is retired.
supabase/migrations_history/20260728172931_fn_undo_correct_uuid_signature.sql :: fn_undo :: scripts/sql/fn_undo_uses_the_real_primary_key.sql :: The 28 Jul migration keyed the undo on a hard-coded id column; fn_undo_uses_the_real_primary_key.sql (3 Sep 2026, applied with read-back) reads the primary key from pg_constraint and matches every key column from the before-image. The two define the same routine but the newer file writes the signature with its DEFAULT clause, which the engine keys as a different text, so without this line the engine kept resolving the superseded migration.
